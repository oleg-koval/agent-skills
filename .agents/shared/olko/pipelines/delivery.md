# Delivery pipeline

1. **Frame.** Product names the actor, observed problem, outcome, evidence, and acceptance checks. A user-approved outcome can proceed with stated uncertainty. Before assigning work, read the target's current `AGENTS.md` and applicable Charter files; record the repository, worktree, branch, HEAD, and pre-existing dirty paths to establish the task baseline.
2. **Design when needed.** Architect resolves ownership, boundaries, failure paths, and compatibility before implementation.
3. **Build.** Engineer uses an isolated workspace and changes the smallest complete slice. Preserve unrelated work.
4. **Prove.** Inspect target-repo check commands and the scripts, setup steps, and hooks they invoke before execution. Run untrusted checks only in a disposable environment without credentials or sensitive filesystem, host, or network access; do not forward host secrets or environment. If isolation is unavailable, report the check as blocked. QA independently checks the behavior and the exact artifact. Add Security when trust, privacy, or supply chain changes materially.
5. **Deliver.** Review the final diff, then create the branch, push, or PR only under the target repo's rules. Apply the pre-PR checks below to every repository, including those without Charter configuration. Use the [review pipeline](review.md) for PR evidence.
6. **Close.** Re-read the authoritative source after each write. Report local correctness, commit, remote SHA, checks, deployment, and human acceptance as separate gates. Name anything incomplete.

Name the requested delivery boundary before allocation: advice, local implementation, PR delivery or release. A status answer, retrospective or file-browser action must not start a repository delivery loop. Local acceptance does not imply authorization to commit, push, merge or deploy. Use host-valid receipt values, separate worker output from lead acceptance, and preserve one concise evidence record rather than rerunning unchanged checks.

Before opening a PR, identify and fetch its actual base and pushed head; for a stack, use the intended parent branch. Run the trusted Charter size preflight against those exact commits and recheck the remote refs immediately before creation. Stop on failure or unavailable evidence; split an oversized change or raise the conflict for an explicit decision. Never change a limit or silently waive a rule. The local check does not prevent direct UI, API, or CLI bypass, and refs can move after a check. See the [ownership map](charter.md#ownership) for where to change each part.

Record the problem and constraints, verify the diff has one concern, run applicable repository checks and secret/whitespace checks, and retain evidence that each commit builds and passes tests. Confirm regressions are prioritized where applicable. Prepare the PR body with `TL;DR (for humans)` first and verify any configured artifact sections. Identify an independent diff reviewer before merge; review and CI are separate from PR creation. Report unavailable or unverified checks rather than treating them as passed. Agent tool hooks must not block; enforce creation checks in the creator itself.

For implementation work delivered through a PR, any completion claim (`DONE`, `DONE_WITH_CONCERNS`, `DELIVERED`, or equivalent) requires passing required local tests and CI on the current head, with no applicable CI failing or in progress. Fix every review finding or rebut it with evidence; reply and verify resolved thread state. Obtain positive completion or satisfaction evidence for each configured required reviewer and each active reviewing bot on that head, including delayed reviews. Inspect each reviewer's actual surface, including PR conversation comments where applicable. Confirm the PR actually merged from its authoritative state. A prior-head review, self-resolved thread, missing or pending review, quota limit, timeout, or unavailable evidence is not satisfaction. Use the target's review workflow with a bounded wait; if a gate remains unknown or incomplete, report `BLOCKED` and the concrete next action. An explicit request to leave a PR open is an exception to the merge gate, not evidence of a merge.

If the target has Charter, apply [its pipeline](charter.md) during build and review. External communication, spending, and publication follow the target's approval rules.

For Apple app work, all leads (including project-specific CSO and CTO agents) must consult [Apple Review](../roles/olko-apple-review.md) before allocating feature tasks and after completion. Require PLAN_APPROVED before allocation and FEATURE_APPROVED before feature closure; require SUBMISSION_READY for the complete candidate before submission handoff. CHANGES_REQUIRED or BLOCKED requires an owned cleanup round and independent re-review; never substitute green tests or a lead self-approval. See the role for evidence and approval invalidation rules.
